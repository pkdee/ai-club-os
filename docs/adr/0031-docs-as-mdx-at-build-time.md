# 0031. Docs 는 저장소의 MDX 로 쓰고 빌드할 때 화면으로 만든다

## 상태

채택. 2026-10-21 에 사용자가 정했습니다.

## 배경

앱을 쓰는 법을 안내할 곳이 없었습니다. 처음 들어온 사람은 무엇부터 하면 되는지, AI Log 를 누가 보는지 같은 것을 운영자에게 물어야 했습니다.

처음에는 문서를 데이터베이스에 두고 앱 안에서 쓰고 고치는 방식을 제안했습니다. 사용자는 "MDX로하고 관리보다는 빌드시에 문서올라가게하자. 그렇게되면 작성자는 나밖에없을거니까 괜찮은거아닐까?" 라고 답했습니다. 문서를 쓰는 사람은 저장소를 고치는 사람 한 명뿐이므로 앱 안의 편집 화면과 권한이 필요 없다는 것입니다.

사용자가 함께 정한 것은 둘입니다.

- 모든 Club 에 같은 문서를 보여 줍니다.
- 코드 블록은 macOS 창 모양으로 두고 복사 버튼을 꼭 넣습니다.

## 결정

### 문서를 두는 곳

- 문서는 `src/content/docs/<slug>.mdx` 에 씁니다.
- 순서는 같은 폴더의 `list.ts` 에 slug 로 적습니다. 목록에 없는 파일은 화면에 나오지 않습니다.
- 제목, 한 줄 소개, 게시한 날, 고친 날, 태그는 문서 맨 앞의 frontmatter 에 적습니다(아래 "frontmatter" 절).
- 시험이 목록과 파일이 서로 맞는지, 문서마다 frontmatter 가 규칙에 맞는지 봅니다.

### 빌드

- `@next/mdx` 가 빌드할 때 MDX 를 React 컴포넌트로 바꿉니다. 요청마다 문서를 다시 읽거나 바꾸지 않습니다.
- Turbopack 은 함수를 넘기지 못하므로 플러그인을 이름과 JSON 옵션으로 `next.config.ts` 에 적습니다.
- 플러그인:
  - `src/features/docs/remark-front-matter.mjs` 가 frontmatter 를 읽어 `export const frontmatter` 로 내보냅니다. 본문 맨 앞의 `#` 제목도 여기서 뺍니다.
  - `remark-gfm` 이 표를 읽습니다.
  - `src/features/docs/remark-markdown.mjs` 가 "마크다운으로 복사" 에 쓸 Markdown 을 만들어 `export const markdown` 으로 내보냅니다.
  - `rehype-slug` 가 제목에 id 를 붙입니다.
  - `src/features/docs/rehype-toc.mjs` 가 그 id 로 목차를 만들어 `export const toc` 로 내보냅니다.
  - `@shikijs/rehype` 가 코드에 색을 칠합니다.
- 목차를 빌드할 때 만든 까닭이 있습니다. 브라우저에서 제목을 읽어 목차를 만들면 effect 안에서 상태를 바꿔야 해서 lint 규칙(`react-hooks/set-state-in-effect`)에 걸립니다. 빌드에서 만들면 서버가 목차를 함께 그리고, 브라우저는 지금 읽는 제목의 표시만 바꿉니다.
- `rehype-toc.mjs` 는 MDX 로더가 Node 에서 바로 불러오므로 TypeScript 가 아닌 `.mjs` 로 썼습니다. 로더가 `.mdx` 파일의 폴더에서 이름을 찾기 때문에 절대 경로로 넘깁니다.

### 화면

- 주소는 `/clubs/<clubId>/docs/<slug>` 입니다.
- 다른 Club 화면처럼 요청마다 소속을 확인합니다. 문서 자체는 Club 의 데이터를 읽지 않습니다.
- 주소의 slug 는 목록에 있을 때만 파일을 불러오고, 없으면 404 입니다.
- `/docs` 로 들어오면 목록의 첫 문서를 엽니다.
- 넓은 화면의 왼쪽 메뉴에 Docs 를 둡니다. 좁은 화면의 아래쪽 메뉴는 여섯 칸이 차 있어서 Club 개요에 Docs 카드를 둡니다.
- 문서 화면 구성:
  - 왼쪽에 문서 목록, 가운데에 본문, 1280px 폭부터 오른쪽에 목차를 둡니다.
  - 아래에 이전 문서와 다음 문서를 둡니다.

### 머리말과 가운데 배치

2026-10-21 에 사용자가 문서를 화면 가운데에 두고, 예시로 든 기술 블로그처럼 제목, 작성일, 태그 등을 보여 달라고 했습니다.

- 세 칸(문서 목록, 본문, 목차)을 Sidebar 를 뺀 영역의 가운데에 둡니다. 목록과 목차의 폭을 같게 두어, 목차가 보이는 폭에서는 본문의 가운데가 그 영역의 가운데와 맞습니다.
  - 1536px 보다 좁으면 목록과 목차를 12rem, 넓으면 14rem 으로 둡니다. 1280px 폭에서도 본문이 480px 남짓 남게 하려는 것입니다.
- 머리말의 차례:
  - 제목과 "마크다운으로 복사" 버튼
  - 한 줄 소개
  - 게시한 날(고쳤으면 고친 날도)과 읽는 데 걸리는 시간
  - 태그
- 머리말의 제목은 frontmatter 의 `title` 입니다. 본문 맨 앞의 `#` 제목은 같은 제목이 두 번 보이지 않게 화면과 "마크다운으로 복사" 에서 뺍니다. 복사할 때는 frontmatter 의 제목과 소개를 맨 앞에 넣습니다.
- 읽는 시간은 복사할 Markdown 의 길이로 어림합니다. 한글은 1분에 500자, 영어와 숫자는 1분에 200낱말로 셉니다. 코드도 함께 세므로 실제보다 길게 나올 수 있어 "약" 을 붙입니다.
- 쓴 사람은 적지 않습니다. 문서를 쓰는 사람이 한 명뿐이기 때문입니다.

### 접는 칸

문서는 복사해 쓰는 템플릿, 긴 예시, 자주 하는 질문을 `<details>` 로 접어 둡니다. MDX 는 본문에 직접 쓴 HTML 태그에는 Docs 컴포넌트를 붙이지 않으므로(시험해 확인했습니다), 브라우저의 기본 모양으로 보였습니다.

- 본문 칸에 `doc-body` 클래스를 두고 `globals.css` 가 그 안의 `details` 와 `summary` 에 모양을 입힙니다.
- 2026-10-21 에 사용자가 기본 토글처럼 보이니 자주 하는 질문의 아코디언처럼 만들자고 해서 모양을 바꿨습니다.
  - 질문 줄은 Label L 이고 오른쪽에 펼침 표시(lucide 의 `chevron-down`)가 있어 펼치면 뒤집힙니다. 브라우저의 기본 삼각형은 감춥니다.
  - 처음에는 테두리를 두른 Card 면의 상자로 그렸습니다. 같은 날 사용자가 이상해 보인다고 했습니다. 칸 하나만 있으면 고르는 칸(select)처럼 보이고, 안에 코드 블록을 넣으면 상자 속 상자가 되었습니다. 그래서 상자를 없애고 위아래에 선만 둡니다. 질문 줄은 본문과 같은 폭에서 시작하고, 안쪽도 본문 폭을 그대로 씁니다.
  - 연달아 놓인 칸은 사이의 선을 하나만 남겨 한 목록으로 읽힙니다.
  - 펼치면 안쪽이 질문 줄 바로 아래에서 살짝 내려오며 나타납니다. 움직임을 줄이도록 설정한 사람에게는 움직이지 않습니다.
  - 높이를 움직이는 `::details-content` 는 쓰지 않습니다. 이것이 들어가면 Turbopack 의 CSS 처리가 파일을 받지 못하고, 개발 서버가 오류 없이 옛 CSS 를 계속 내주었습니다.
- 브라우저의 `details` 를 그대로 쓰므로 키보드와 화면 읽기 프로그램이 따로 손대지 않아도 동작합니다.
- 안쪽의 문단, 목록, 코드 블록은 Docs 컴포넌트가 그대로 그립니다.
- 무엇을 접을지는 문서 사이에서 한결같게 둡니다. 복사해 쓰는 템플릿과 프롬프트 전문, 긴 예시는 언제나 접고, 설명 흐름 안의 짧은 비교 예시는 펼쳐 둡니다. 문서마다 `## 자주 하는 질문` 을 두고 질문마다 칸 하나를 씁니다. 쓰는 법은 `src/content/docs/README.md` 에 있습니다.
- 컴포넌트(`<Details>`)를 따로 만들지 않은 까닭은 "마크다운으로 복사" 에 있습니다. 소문자 HTML 태그는 Markdown 에 그대로 남아 GitHub 같은 곳에서도 접혀 보이지만, 다른 컴포넌트는 감싼 글만 남아 제목 줄을 잃습니다.

### 코드 블록

- macOS 창처럼 위쪽 막대에 빨강, 노랑, 초록의 창 단추와 언어 이름, 복사 버튼을 둡니다.
  - 창 단추는 꾸밈이라 누를 수 없습니다.
  - 점의 색은 아이콘 토큰(`icon-danger`, `icon-warning`, `icon-success`)을 씁니다.
- 색은 Shiki 의 `github-light-default` 와 `github-dark-default` 테마를 씁니다.
  - Shiki 는 두 색을 변수로만 적고, `globals.css` 가 화면 모드에 맞는 쪽을 고릅니다.
  - `-default` 테마를 고른 까닭은 가장 흐린 글자(주석)도 코드 블록 배경과의 대비가 4.5:1 을 넘기 때문입니다. 밝은 화면에서 4.55:1, 어두운 화면에서 5.76:1 입니다. 같은 계산에서 `github-light` 는 3.49:1 이었습니다.
- Shiki 는 쓰인 언어만 빌드할 때 불러옵니다. 모르는 언어와 언어를 적지 않은 블록은 색 없이 보여 줍니다.
- 복사 버튼은 같은 블록의 코드를 그대로 복사합니다. 브라우저가 막으면 "복사 실패" 를 보여 주고, 화면 읽기 프로그램에 직접 복사하라고 알립니다.

### 마크다운으로 복사

2026-10-21 에 사용자가 문서를 Markdown 으로 복사하는 버튼을 더해 달라고 했습니다. 문서 제목 옆에 "마크다운으로 복사" 버튼을 둡니다.

- Markdown 은 빌드할 때 MDX 원문에서 만듭니다. 원문을 그대로 살리고 MDX 에만 있는 것만 바꿉니다.
  - `Callout` 은 GitHub 의 알림 인용(`> [!NOTE]`, `> [!TIP]`, `> [!WARNING]`, `> [!CAUTION]`)으로 바꿉니다. tone 의 info, success, warning, danger 에 차례로 맞춥니다. 제목은 굵은 글씨의 첫 줄이 됩니다.
  - `import`, `export` 와 `{}` 식은 뺍니다.
  - `details` 처럼 소문자로 시작하는 HTML 태그는 Markdown 에서도 쓰이므로 그대로 둡니다. 다른 컴포넌트는 감싼 내용만 남깁니다.
  - 코드 블록, 표, 목록은 손대지 않습니다.
- 앱 안으로 가는 링크(`/`, `./`, `../` 로 시작)는 Club 주소를 알아야 풀 수 있습니다. 그래서 빌드할 때는 `{ href }` 로 따로 두고, 버튼을 누를 때 브라우저가 지금 주소를 기준으로 전체 주소로 바꿉니다. 바깥 주소와 `#` 로 시작하는 제목 링크는 그대로 둡니다.
- 맨 앞에는 frontmatter 의 제목과 소개를 둡니다. frontmatter 와 본문 맨 앞의 `#` 제목은 넣지 않습니다.
- 새 패키지는 더하지 않았습니다. 원문을 다시 쓰지 않고 잘라 이으므로 Markdown 을 쓰는 도구가 필요 없습니다.

### frontmatter

2026-10-21 에 사용자가 문서 맨 앞에 `---` 줄로 감싼 `title` 과 `description` 을 적었는데 화면이 깨졌습니다. MDX 는 frontmatter 를 몰라서 그 칸을 가로줄과 `##` 제목으로 그렸고, 그 제목이 목차에도 들어갔습니다. 사용자가 MDX 에 맞게 화면을 꾸려 달라고 했습니다.

- 문서마다의 값(제목, 한 줄 소개, 게시한 날, 고친 날, 태그)은 그 문서의 frontmatter 에 둡니다. `list.ts` 에는 순서만 남깁니다. 한 문서의 값이 두 곳에 나뉘면 어느 쪽이 화면에 보이는지 헷갈리기 때문입니다.
- `title` 과 `description` 은 꼭 적고 `published`, `updated`, `tags` 는 빼도 됩니다. 사용자가 세 문서 모두 제목과 소개만 적었기 때문입니다. 날짜와 태그는 적은 문서에만 머리말에 보입니다. 모르는 이름, 있지 않은 날, `#` 을 붙인 태그는 빌드를 멈추고 몇 번째 줄이 왜 틀렸는지 알립니다. 시험도 같은 함수(`src/features/docs/front-matter.mjs`)로 저장소의 문서를 봅니다.
- YAML 의 일부만 읽습니다. 한 줄에 `이름: 값` 하나, 목록은 `[가, 나]` 나 `- 가` 줄, 따옴표와 줄 끝의 `#` 설명입니다. 값은 날짜도 글로 읽습니다.
- `src/features/docs/remark-front-matter.mjs` 가 MDX 의 parser 를 감싸, MDX 가 읽기 전에 frontmatter 를 같은 길이의 빈칸으로 바꿉니다.
  - 그대로 두면 값에 `{` 나 `<` 가 있을 때 MDX 가 식이나 태그로 읽다가 멈춥니다.
  - 길이와 줄이 그대로라 원문의 위치로 잘라 쓰는 Markdown 플러그인과 어긋나지 않습니다.
- 읽은 값은 `export const frontmatter` 로 내보냅니다. 서버의 `listDocs`, `findDoc`, `loadDoc`(`src/features/docs/load.ts`)이 목록의 slug 로 모듈을 불러 이 값을 씁니다. 문서 목록은 Docs 의 layout 이 이 값을 받아 그립니다.
- 사용자가 frontmatter 의 제목을 본문 맨 앞에 `#` 제목으로 다시 적었습니다. 이 줄은 머리말과 겹치므로 화면과 복사할 Markdown 에서 뺍니다. 글이 `title` 과 다르면 어느 쪽이 맞는지 알 수 없어 빌드를 멈춥니다. 다른 곳의 `#` 제목도 멈춥니다. 이전에 첫 `#` 제목을 머리말로 옮기던 `rehype-lead-title.mjs` 는 지웠습니다.
- 새 패키지는 더하지 않았습니다. 대안은 아래에 적었습니다.

## 결과

- 문서를 고치거나 더하려면 저장소를 고치고 다시 배포해야 합니다. 앱 안에서는 고칠 수 없습니다.
- 문서는 Club 소속이 있어야 보이지만 저장소에 그대로 들어 있습니다. 저장소를 공개하면 문서도 공개됩니다. 비밀 값이나 개인 정보를 적지 않습니다.
- 패키지 7개를 직접 더했습니다. 설치 전후의 `npm audit` 결과는 높음 9건으로 같습니다.
  - 실행할 때 쓰는 것: `@next/mdx`, `@mdx-js/loader`, `@mdx-js/react`, `remark-gfm`, `rehype-slug`, `@shikijs/rehype`
  - 타입: `@types/mdx`
  - `shiki` 는 `@shikijs/rehype` 를 따라 들어옵니다.
- 코드 블록 안의 글자 색은 GitHub 테마의 값이라 디자인 토큰이 아닙니다. `DESIGN.md` 의 "16진수 값을 직접 쓰지 않는다" 규칙의 예외로 적었습니다.
- 문서 안의 링크:
  - 앱의 다른 화면은 Club id 없이 상대 경로로 겁니다. 예를 들어 `../logs/new` 는 AI Log 쓰기로 갑니다.
  - 다른 문서는 `./<slug>` 로 겁니다.
  - 바깥 주소는 새 탭에서 열립니다.
- 시험:
  - 목록과 파일이 맞는지, slug 의 모양, 문서마다 frontmatter 가 규칙에 맞는지 봅니다.
  - 문서 안의 링크가 있는 화면(`src/app` 의 page.tsx), 목록에 있는 문서, 그 문서의 제목 id 를 가리키는지 봅니다(`links.test.ts`). 빌드와 같은 플러그인으로 문서를 바꿔 id 를 모읍니다. 2026-10-21 에 사용자가 새로 쓴 문서가 아직 없는 문서 12곳으로 링크를 걸고 있던 것을 계기로 더했습니다. 바깥 주소는 열어 보지 않고 https 인지만 봅니다.
  - frontmatter 를 읽는 함수가 따옴표, 목록, 설명을 다루고 틀린 값마다 까닭을 알리는지 봅니다.
  - 앞뒤 문서와 언어 이름을 봅니다.
  - 목차 플러그인이 h2, h3 를 차례대로 모으는지 봅니다.
  - Markdown 플러그인은 `@mdx-js/loader` 와 같은 컴파일러(`@mdx-js/mdx`)로 MDX 를 모듈까지 만들어 내보낸 값을 봅니다. 이 컴파일러는 `@mdx-js/loader` 를 따라 들어온 것이라 시험에서만 직접 부릅니다.
  - 복사할 글이 링크를 전체 주소로 바꾸고 제목을 알맞게 붙이는지 봅니다.
  - frontmatter 플러그인은 같은 컴파일러로 모듈을 만들어 내보낸 값, 그린 본문, 복사할 Markdown 을 봅니다. 맨 앞의 `#` 제목을 빼는지, 틀린 frontmatter 와 다른 곳의 `#` 제목에서 멈추는지도 봅니다.
  - 날짜를 한국어로 적는 것과 읽는 시간의 어림을 봅니다.
- 화면의 흐름은 자동으로 확인하지 않습니다(`0010`). 개발 서버에서 넓은 화면과 좁은 화면, 두 화면 모드, 복사, 목차 이동을 손으로 확인했습니다.

## 검토할 대안

- **데이터베이스에 두고 앱에서 쓰기**: 다시 배포하지 않고 고칠 수 있습니다. 대신 쓰기 화면, 권한, 수정 기록, 테이블이 필요합니다. 쓰는 사람이 한 명이라 그만한 값이 없습니다.
- **Markdown 만 쓰기**: 더 단순합니다. 대신 Callout 같은 컴포넌트를 본문에 넣지 못합니다.
- **목차를 브라우저에서 만들기**: 플러그인이 필요 없습니다. 대신 화면을 그린 뒤 목차가 나타나고, effect 안에서 상태를 바꾸는 lint 규칙에 걸립니다.
- **`rehype-pretty-code` 나 `rehype-highlight`**: 앞의 것은 Shiki 위에 기능을 더 얹고, 뒤의 것은 테마를 CSS 로 따로 둡니다. 쓰는 기능만 있는 Shiki 의 공식 플러그인을 골랐습니다.
- **Club 마다 다른 문서**: Club 이 자기 안내를 둘 수 있습니다. 하지만 지금은 앱 사용법이라 모두에게 같습니다.
- **화면의 HTML 을 브라우저에서 Markdown 으로 바꾸기**: 플러그인이 필요 없습니다. 대신 바꾸는 패키지(`turndown` 등)를 더해야 하고, 코드 블록의 색 표시와 Callout 의 아이콘을 다시 걷어 내야 합니다.
- **MDX 원문을 그대로 복사하기**: 가장 단순합니다. 대신 `<Callout>` 같은 태그가 남고 상대 경로 링크가 다른 곳에서는 열리지 않습니다.
- **`remark-frontmatter` 와 `yaml` 패키지**: frontmatter 를 읽는 흔한 방법이고 YAML 전부를 읽습니다. 둘 다 `@google/design.md` 를 따라 이미 들어와 있지만 직접 쓰려면 의존성으로 더해야 합니다. 문서에 적는 값은 다섯 가지 글과 목록뿐이라 직접 읽기로 했습니다. 값이 늘어 YAML 의 다른 기능이 필요해지면 이 패키지로 바꿉니다.
- **값은 `list.ts` 에 두고 frontmatter 는 무시하기**: 코드가 가장 적게 바뀝니다. 대신 사용자가 쓰려는 MDX 의 흔한 모양과 다르고, 같은 값을 두 곳에 적게 됩니다.
