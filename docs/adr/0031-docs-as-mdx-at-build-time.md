# 0031. Docs 는 저장소의 MDX 로 쓰고 빌드할 때 화면으로 만든다

## 상태

채택. 2026-10-21 에 사용자가 정했습니다.

## 배경

앱을 쓰는 법을 안내할 곳이 없었습니다. 처음 들어온 사람은 무엇부터 하면 되는지, AI Log 를 누가 보는지 같은 것을 운영자에게 물어야 했습니다.

처음에는 문서를 데이터베이스에 두고 앱 안에서 쓰고 고치는 방식을 제안했습니다. 사용자는 "MDX로하고 관리보다는 빌드시에 문서올라가게하자. 그렇게되면 작성자는 나밖에없을거니까 괜찮은거아닐까?" 라고 답했습니다. 문서를 쓰는 사람은 저장소를 고치는 사람 한 명뿐이므로 앱 안의 편집 화면과 권한이 필요 없다는 것입니다.

사용자가 함께 정한 것은 둘입니다.

- 모든 Club 에 같은 문서를 보여 줍니다.
- 코드 블록은 macOS 창 모양으로 두고 복사 버튼을 꼭 넣습니다.

## 결정

### 문서를 두는 곳

- 문서는 `src/content/docs/<slug>.mdx` 에 씁니다.
- 순서와 제목, 한 줄 소개는 같은 폴더의 `list.ts` 에 적습니다. 목록에 없는 파일은 화면에 나오지 않습니다.
- 시험이 목록과 파일이 서로 맞는지 봅니다.
- 문서 제목은 목록의 `title` 이 보여 줍니다. 본문은 `##` 부터 씁니다.

### 빌드

- `@next/mdx` 가 빌드할 때 MDX 를 React 컴포넌트로 바꿉니다. 요청마다 문서를 다시 읽거나 바꾸지 않습니다.
- Turbopack 은 함수를 넘기지 못하므로 플러그인을 이름과 JSON 옵션으로 `next.config.ts` 에 적습니다.
- 플러그인:
  - `remark-gfm` 이 표를 읽습니다.
  - `rehype-slug` 가 제목에 id 를 붙입니다.
  - `src/features/docs/rehype-toc.mjs` 가 그 id 로 목차를 만들어 `export const toc` 로 내보냅니다.
  - `@shikijs/rehype` 가 코드에 색을 칠합니다.
- 목차를 빌드할 때 만든 까닭이 있습니다. 브라우저에서 제목을 읽어 목차를 만들면 effect 안에서 상태를 바꿔야 해서 lint 규칙(`react-hooks/set-state-in-effect`)에 걸립니다. 빌드에서 만들면 서버가 목차를 함께 그리고, 브라우저는 지금 읽는 제목의 표시만 바꿉니다.
- `rehype-toc.mjs` 는 MDX 로더가 Node 에서 바로 불러오므로 TypeScript 가 아닌 `.mjs` 로 썼습니다. 로더가 `.mdx` 파일의 폴더에서 이름을 찾기 때문에 절대 경로로 넘깁니다.

### 화면

- 주소는 `/clubs/<clubId>/docs/<slug>` 입니다.
- 다른 Club 화면처럼 요청마다 소속을 확인합니다. 문서 자체는 Club 의 데이터를 읽지 않습니다.
- 주소의 slug 는 목록에 있을 때만 파일을 불러오고, 없으면 404 입니다.
- `/docs` 로 들어오면 목록의 첫 문서를 엽니다.
- 넓은 화면의 왼쪽 메뉴에 Docs 를 둡니다. 좁은 화면의 아래쪽 메뉴는 여섯 칸이 차 있어서 Club 개요에 Docs 카드를 둡니다.
- 문서 화면 구성:
  - 왼쪽에 문서 목록, 가운데에 본문, 1280px 폭부터 오른쪽에 목차를 둡니다.
  - 아래에 이전 문서와 다음 문서를 둡니다.

### 코드 블록

- macOS 창처럼 위쪽 막대에 빨강, 노랑, 초록의 창 단추와 언어 이름, 복사 버튼을 둡니다.
  - 창 단추는 꾸밈이라 누를 수 없습니다.
  - 점의 색은 아이콘 토큰(`icon-danger`, `icon-warning`, `icon-success`)을 씁니다.
- 색은 Shiki 의 `github-light-default` 와 `github-dark-default` 테마를 씁니다.
  - Shiki 는 두 색을 변수로만 적고, `globals.css` 가 화면 모드에 맞는 쪽을 고릅니다.
  - `-default` 테마를 고른 까닭은 가장 흐린 글자(주석)도 코드 블록 배경과의 대비가 4.5:1 을 넘기 때문입니다. 밝은 화면에서 4.55:1, 어두운 화면에서 5.76:1 입니다. 같은 계산에서 `github-light` 는 3.49:1 이었습니다.
- Shiki 는 쓰인 언어만 빌드할 때 불러옵니다. 모르는 언어와 언어를 적지 않은 블록은 색 없이 보여 줍니다.
- 복사 버튼은 같은 블록의 코드를 그대로 복사합니다. 브라우저가 막으면 "복사 실패" 를 보여 주고, 화면 읽기 프로그램에 직접 복사하라고 알립니다.

## 결과

- 문서를 고치거나 더하려면 저장소를 고치고 다시 배포해야 합니다. 앱 안에서는 고칠 수 없습니다.
- 문서는 Club 소속이 있어야 보이지만 저장소에 그대로 들어 있습니다. 저장소를 공개하면 문서도 공개됩니다. 비밀 값이나 개인 정보를 적지 않습니다.
- 패키지 7개를 직접 더했습니다. 설치 전후의 `npm audit` 결과는 높음 9건으로 같습니다.
  - 실행할 때 쓰는 것: `@next/mdx`, `@mdx-js/loader`, `@mdx-js/react`, `remark-gfm`, `rehype-slug`, `@shikijs/rehype`
  - 타입: `@types/mdx`
  - `shiki` 는 `@shikijs/rehype` 를 따라 들어옵니다.
- 코드 블록 안의 글자 색은 GitHub 테마의 값이라 디자인 토큰이 아닙니다. `DESIGN.md` 의 "16진수 값을 직접 쓰지 않는다" 규칙의 예외로 적었습니다.
- 문서 안의 링크:
  - 앱의 다른 화면은 Club id 없이 상대 경로로 겁니다. 예를 들어 `../logs/new` 는 AI Log 쓰기로 갑니다.
  - 다른 문서는 `./<slug>` 로 겁니다.
  - 바깥 주소는 새 탭에서 열립니다.
- 시험:
  - 목록과 파일이 맞는지, slug 의 모양을 봅니다.
  - 앞뒤 문서와 언어 이름을 봅니다.
  - 목차 플러그인이 h2, h3 를 차례대로 모으는지 봅니다.
- 화면의 흐름은 자동으로 확인하지 않습니다(`0010`). 개발 서버에서 넓은 화면과 좁은 화면, 두 화면 모드, 복사, 목차 이동을 손으로 확인했습니다.

## 검토할 대안

- **데이터베이스에 두고 앱에서 쓰기**: 다시 배포하지 않고 고칠 수 있습니다. 대신 쓰기 화면, 권한, 수정 기록, 테이블이 필요합니다. 쓰는 사람이 한 명이라 그만한 값이 없습니다.
- **Markdown 만 쓰기**: 더 단순합니다. 대신 Callout 같은 컴포넌트를 본문에 넣지 못합니다.
- **목차를 브라우저에서 만들기**: 플러그인이 필요 없습니다. 대신 화면을 그린 뒤 목차가 나타나고, effect 안에서 상태를 바꾸는 lint 규칙에 걸립니다.
- **`rehype-pretty-code` 나 `rehype-highlight`**: 앞의 것은 Shiki 위에 기능을 더 얹고, 뒤의 것은 테마를 CSS 로 따로 둡니다. 쓰는 기능만 있는 Shiki 의 공식 플러그인을 골랐습니다.
- **Club 마다 다른 문서**: Club 이 자기 안내를 둘 수 있습니다. 하지만 지금은 앱 사용법이라 모두에게 같습니다.
