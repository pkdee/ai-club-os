# 0011. AI Log 검색은 데이터베이스 함수가 맡고 조건은 주소에 담는다

## 상태

채택. 2026-10-10. 글자를 비교하는 방식은 같은 날 `0012-loose-matching-for-search-and-tools.md` 로 바꿨습니다. 아래의 "글자가 포함되는지를 봅니다" 와 도구를 정확히 같은 이름으로 고르는 부분은 그 문서를 따릅니다.

## 배경

AI Log 목록에 설계대로 검색과 Session, 도구, 정렬 고르기를 넣기로 했습니다. 찾는 글자는 제목, 네 가지 내용 칸, 도구 이름 가운데 어디에 있어도 찾아야 합니다.

Supabase 의 Data API 로 여러 열을 한꺼번에 찾으려면 조건을 하나의 문자열로 이어 붙여 보내야 합니다. 사용자가 넣은 글자를 그 문자열에 끼워 넣으면 쉼표나 괄호, 따옴표가 조건의 문법으로 읽혀서 조건이 깨지거나 의도하지 않은 조건이 붙을 수 있습니다.

도구로 고르는 칸에는 그 Club 에서 쓰인 도구 이름의 목록이 필요한데, 도구는 기록마다 배열로 들어 있어서 조회만으로는 목록을 만들 수 없습니다.

## 결정

- 검색은 `public.search_ai_logs(target_club_id, search)` 함수가 합니다. 찾는 글자는 함수의 값으로 넘기므로 조건 문자열에 끼워 넣지 않습니다.
- 이 함수는 부른 사람의 권한으로 실행합니다. `ai_logs` 의 접근 규칙이 그대로 적용되어 자기 Club 의 기록만 나옵니다.
- 대소문자를 가리지 않고 글자가 포함되는지를 봅니다. 찾는 글자의 `%` 와 `_` 는 글자 그대로 찾습니다.
- 함수가 돌려주는 모양은 `ai_logs` 와 같습니다. 그래서 앱은 그 뒤에 Session, 도구, 작성자 조건과 정렬, 작성자와 Session 이름 읽기를 평소 조회와 같은 방식으로 이어 붙입니다.
- 도구 목록은 `public.club_tool_counts(target_club_id)` 함수가 많이 쓰인 순서로 돌려줍니다. 이것도 부른 사람의 권한으로 실행합니다.
- 조건은 모두 주소에 담습니다(`q`, `session`, `tool`, `sort`, `view`, `n`). 새로 고치거나 주소를 공유해도 같은 목록이 보입니다. 주소의 값을 조건으로 바꾸는 일은 `src/features/ai-log/filters.ts` 한 곳에서 합니다.
- 같은 시각에 만든 기록끼리도 순서가 바뀌지 않도록 만든 시각 다음에 식별자로 한 번 더 정렬합니다.

## 결과

- 검색은 그 Club 의 기록을 모두 훑습니다. 색인을 쓰지 않습니다. 한 Club 의 기록이 수천 건을 넘기 전에는 문제가 없을 것으로 보지만 재 보지는 않았습니다. 느려지면 `pg_trgm` 색인이나 전문 검색으로 바꿉니다.
- 띄어쓰기나 조사가 다르면 찾지 못합니다. "청크 크기" 로는 "청크크기" 를 찾지 못합니다.
- 도구로 고르는 것은 이름이 정확히 같은 기록만 찾습니다. "ChatGPT" 와 "chatgpt" 는 다른 도구로 나옵니다. 도구 이름의 표기를 맞추는 방법은 여전히 정해야 할 항목입니다.
- 목록은 한 번에 200개까지만 보여 주는 제한이 그대로 있습니다. 더 오래된 기록은 찾는 글자나 조건으로 좁혀서 봅니다.
- 접근 규칙 시험에 두 함수의 시험 19건을 더했습니다. 앱이 보내는 요청 12가지는 PostgREST 를 붙여 손으로 확인했고 자동 검증에는 들어 있지 않습니다.

## 검토할 대안

- **조건 문자열에 찾는 글자를 끼워 넣기**: 함수가 필요 없습니다. 하지만 글자를 문법에 맞게 감싸는 일을 앱이 정확히 해야 하고, 틀리면 조건이 깨집니다.
- **전문 검색이나 `pg_trgm`**: 기록이 많아도 빠르고 비슷한 글자도 찾습니다. 한국어 전문 검색은 따로 설정이 필요하고, 지금 규모에는 과합니다.
- **기록을 모두 받아 브라우저에서 거르기**: 서버 쪽 변경이 없습니다. 기록이 늘수록 느려지고 200개 제한 밖의 기록은 찾지 못합니다.
- **조건을 화면 상태로만 두기**: 구현이 짧습니다. 새로 고치면 조건이 사라지고 주소로 공유할 수 없습니다.
