# 0005. Attendance 를 Member 와 Session 사이의 행으로 두고 Member 이름을 members 에 둔다

## 상태

채택. 2026-10-10.

## 배경

Attendance 는 한 Session 에 어느 Member 가 어떻게 참여했는지를 남기는 기록입니다. 화면은 Session 마다 Member 를 줄지어 보여 주고 운영자가 출석, 지각, 결석, 공결 가운데 하나를 고릅니다.

이 화면을 만들려면 두 가지가 먼저 필요했습니다.

- 다른 Member 의 이름을 보여 줄 방법. 이름은 Supabase Auth 의 `auth.users` 에 있는데 이 테이블은 Data API 에 노출되지 않아 앱이 읽을 수 없습니다. `docs/adr/0003-club-membership-and-rls.md` 에서 미뤄 둔 문제입니다.
- 기록이 다른 Club 의 Session 이나 Member 를 가리키지 못하게 막을 방법. 접근 규칙이 `club_id` 하나만 보고 판단하면, 자기 Club 의 번호를 적고 남의 Session 번호를 넣는 요청이 통과합니다.

## 결정

- `members` 에 `display_name` 과 `email` 열을 둡니다. Club 에 참여할 때 Google 계정의 이름과 이메일을 옮겨 적습니다. 이름이 없으면 이메일을 이름으로 씁니다.
- 이미 있던 Member 는 마이그레이션이 `auth.users` 에서 값을 읽어 채웁니다.
- Attendance 는 `attendance` 테이블의 행으로 둡니다. 한 Session 의 한 Member 에게 행은 하나뿐입니다.
- 행이 없으면 미기록입니다. 미기록을 값으로 저장하지 않습니다.
- 상태는 `present`, `late`, `absent`, `excused` 네 가지를 check 제약으로 둡니다. 종류가 잠정 결정이라 고치기 쉬운 방식을 골랐습니다.
- `attendance` 는 `club_id` 를 직접 가지고, `(session_id, club_id)` 와 `(member_id, club_id)` 두 묶음으로 `sessions` 와 `members` 를 가리킵니다. 그래서 Session 과 Member 가 같은 Club 에 속할 때만 행을 만들 수 있습니다.
- 조회는 같은 Club 의 Member 모두에게 허용합니다. 기록, 수정, 삭제는 운영자만 합니다.
- 고칠 수 있는 열은 `status` 뿐입니다. 누구의 어느 회차 기록인지는 바꿀 수 없습니다.
- 마지막으로 기록한 사람과 시각은 trigger 가 남깁니다. 앱이 보낸 값을 믿지 않습니다.

## 결과

- Member 이름은 참여한 시점의 값입니다. 사용자가 Google 계정의 이름을 바꿔도 따라 바뀌지 않습니다. 이름을 고치는 기능은 Member 화면을 만들 때 다룹니다.
- 같은 Club 의 Member 는 서로의 이메일을 볼 수 있습니다. `members` 조회가 이미 같은 Club 으로 제한되어 있어 다른 Club 에는 보이지 않습니다.
- 이름은 화면 표시에만 씁니다. 사용자가 고칠 수 있는 값이므로 접근 규칙에는 쓰지 않습니다.
- 미기록으로 되돌리려면 행을 지웁니다. 그래서 운영자에게 `attendance` 삭제를 허용했습니다. 다른 테이블에는 아직 삭제 규칙이 없습니다.
- Session 이나 Member 가 삭제되면 그 기록도 함께 삭제됩니다. 탈퇴한 Member 의 기록을 남길지는 삭제 정책을 정할 때 다시 봅니다.
- 이전 상태는 남지 않습니다. 고치면 마지막 값과 마지막으로 고친 사람만 남습니다. 수정 기록을 남길지는 아직 결정이 필요한 항목입니다.
- 접근 규칙은 로컬 Postgres 17 에서 운영자, 구성원, 다른 Club 의 운영자, 로그인하지 않은 요청으로 14가지 경우를 손으로 시험했습니다. 다른 Club 의 Session 이나 Member 를 가리키는 요청이 외래 키에서 거부되는 것도 포함합니다.

## 검토할 대안

- **프로필 테이블을 따로 둠**: 사용자마다 이름을 한 곳에서 관리할 수 있습니다. 하지만 같은 Club 사람에게만 보이게 하려면 프로필 조회 규칙이 `members` 를 거쳐야 하고, 지금은 이름과 이메일 말고 담을 것이 없습니다. Club 마다 다른 이름을 쓸 여지도 사라집니다.
- **`auth.users` 를 읽는 함수를 노출**: 값을 옮겨 적지 않아도 되지만 인증 테이블을 읽는 통로가 하나 더 생깁니다. 노출 범위를 줄이려고 택하지 않았습니다.
- **미기록을 상태 값으로 저장**: 행이 항상 있어 읽기가 단순해집니다. 대신 Session 을 만들거나 Member 가 참여할 때마다 행을 미리 만들어야 하고, 빠뜨리면 화면과 어긋납니다.
- **`club_id` 없이 Session 을 거쳐 Club 을 확인**: 열이 하나 줄지만 접근 규칙이 매번 `sessions` 를 다시 읽어야 하고, Member 가 같은 Club 인지는 여전히 따로 확인해야 합니다.
- **본인이 직접 출석을 기록**: 운영자의 일이 줄지만 기록의 신뢰가 떨어집니다. 화면 설계에서 Attendance 기록을 운영자의 일로 그렸으므로 그대로 따랐습니다.
