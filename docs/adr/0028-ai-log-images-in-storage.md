# 0028. AI Log 의 이미지는 Storage 에 두고, 목록에 먼저 적은 자리에만 올린다

## 상태

채택. 2026-10-11 에 정하고 2026-10-12 에 구현을 마쳤습니다. Supabase Storage 를 처음 씁니다.

## 배경

AI Log 는 글뿐이었습니다. 화면을 찍은 것이나 결과 그림을 보여 줄 수 없어 시도한 내용을 말로 길게 풀어야 했습니다.

사용자가 정했습니다. 이미지만 받는다. PNG, JPEG, WebP, GIF 를 한 기록에 4장, 한 장에 5MB 까지 붙인다. 같은 Club 의 Member 만 본다. AI 로 보내지 않고 발표에도 넣지 않는다.

## 결정

### 두는 곳

- 파일은 Supabase Storage 의 `ai-log-images` 에 둡니다. 공개하지 않는 저장 공간입니다.
- 어떤 기록에 무엇이 붙었는지는 `ai_log_attachments` 에 한 줄씩 적습니다.
- 경로는 Club, 기록, 파일 이름의 세 마디입니다. 파일 이름은 앱이 만든 식별자와 확장자이고, 사용자가 올린 파일의 이름은 쓰지 않습니다.
- 형식과 크기는 세 곳에서 같은 값으로 막습니다. 앱, 목록의 제약, 저장 공간의 설정입니다.
- SVG 는 받지 않습니다. 안에 스크립트를 담을 수 있습니다.

### 올리는 순서

1. 앱의 서버가 목록에 줄을 먼저 적습니다. 작성자인지와 장수 제한을 이때 데이터베이스가 확인합니다.
2. 서버가 그 자리에만 쓸 수 있는 한 번짜리 표를 Storage 에서 받아 브라우저에 줍니다.
3. 브라우저가 그 표로 Storage 에 바로 올립니다. 파일은 앱의 서버를 거치지 않습니다.
4. 올리지 못하면 적어 둔 줄을 거둡니다.

- 브라우저에서 쓰는 Storage 연결은 로그인 정보를 싣지 않습니다. 표가 자리와 권한을 정합니다.
- 서버를 거치지 않는 까닭은 배포 서비스가 요청 하나의 크기를 5MB 보다 작게 막기 때문입니다.

### 접근 규칙

- 작성자만 자기 기록에 붙입니다. 작성자와 운영자가 지웁니다. Member 는 모두 봅니다.
- Storage 에도 같은 규칙을 둡니다. 여기에 한 가지를 더합니다. 목록에 내가 적어 둔 경로에만 올릴 수 있습니다.
- 올린 사람은 Club 에서 나간 뒤에도 자기 파일을 읽고 지울 수 있습니다. 계정을 지우기 전에 자기 파일을 거둘 수 있어야 하기 때문입니다(`0027`).
- 화면에는 한 시간 동안만 쓸 수 있는 주소를 만들어 보여 줍니다. 화면을 열 때마다 새로 만듭니다.

### 파일과 목록을 맞춰 두기

- 파일이 Storage 에 남아 있는 동안에는 목록의 줄을 지우지 못합니다. 데이터베이스의 trigger 가 막습니다.
- 그래서 지울 때는 언제나 파일이 먼저입니다. 이미지 한 장을 지울 때, AI Log 를 지울 때, Club 을 지울 때, 계정을 지울 때 모두 같습니다. 파일을 빠뜨리면 지우는 일 전체가 되돌려집니다.
- 올리는 쪽은 목록에 적힌 자리에만 올릴 수 있고, 지우는 쪽은 파일이 없어야 줄을 지울 수 있습니다. 두 규칙으로 목록에 없는 파일이 생기지 않습니다.
- 줄은 있는데 파일이 없는 경우는 생길 수 있습니다. 올리다가 창을 닫았을 때입니다. 작성자와 운영자에게 파일이 없는 이미지라고 보여 주고 지울 수 있게 합니다. 다른 Member 에게는 보이지 않습니다.

### 적용 전

- 마이그레이션을 적용하기 전에는 이미지 영역이 나오지 않고, AI Log 와 Club 을 지우는 일도 그대로 동작합니다.

## 결과

- AI Log 와 Club 을 지우는 일이 Storage 가 응답하는지에 기댑니다. 파일을 지우지 못하면 지우지 않고 다시 시도하라고 안내합니다.
- 이미지를 설명하는 글을 따로 받지 않습니다. 화면 낭독기에는 어느 기록에 붙인 몇째 이미지인지만 읽힙니다. 내용은 기록의 글로 전해야 합니다.
- 주소가 한 시간 뒤에 끊깁니다. 화면을 오래 열어 두면 이미지를 크게 보는 링크가 열리지 않고, 새로 고치면 다시 됩니다.
- 주소를 받은 사람은 그 한 시간 동안 로그인하지 않아도 그 이미지를 봅니다. Member 가 주소를 밖으로 옮기는 것까지 막지는 못합니다.
- Storage 는 올릴 때 적어 낸 형식만 확인합니다. 파일의 내용까지 들여다보지는 않습니다. 이미지가 아닌 것을 이미지라고 적어 올리면 받아들이지만, 브라우저는 그것을 이미지로만 다룹니다.
- 줄을 적어 표를 받은 뒤 줄을 지우고 그 표로 올리면 목록에 없는 파일이 하나 생깁니다. 작성자가 일부러 해야 생기는 일이고 5MB 를 넘지 못합니다. 막지 않았습니다.
- Club 마다 쓸 수 있는 용량의 한도는 두지 않았습니다.
- 접근 규칙 시험 84건과 로컬에 띄운 Storage 서비스에서의 확인이 이 규칙들을 봅니다. 실제 Supabase 프로젝트에서는 이 저장소에서 확인하지 못했습니다.

## 로컬 Storage 서비스에서 확인한 것

Supabase 의 Storage 서비스를 로컬에 띄우고 이 마이그레이션을 적용해 확인했습니다.

- 목록에 적은 자리에는 표로 올라가고, 올린 파일의 주인은 표를 받은 사람으로 적힙니다.
- 목록에 적지 않은 자리, 남이 적어 둔 자리의 표는 받지 못합니다.
- 같은 표로 두 번 올리지 못합니다.
- 형식이 다른 파일과 5MB 를 넘는 파일은 Storage 가 거절합니다. 5MB 에 꼭 맞는 파일은 받습니다.
- 지울 권한이 없는 파일을 지우려 하면 오류 없이 0개가 지워집니다.
- 올린 사람의 계정이 지워져도 Storage 는 막지 않고 파일을 남깁니다. 그래서 파일이 남은 줄을 지우지 못하게 하는 규칙을 데이터베이스에 두었습니다.

## 검토할 대안

- **파일을 앱의 서버로 받아서 올림**: 서버가 내용을 확인할 수 있습니다. 배포 서비스의 요청 크기 제한에 걸리고 서버가 큰 파일을 붙들고 있어야 합니다.
- **브라우저가 로그인 정보로 바로 올림**: 표를 받는 단계가 없습니다. 브라우저에도 로그인을 갱신하는 연결이 하나 더 생기고, 올릴 자리를 브라우저가 정하게 됩니다.
- **파일을 먼저 올리고 목록에 적음**: 올리지 못한 줄이 남지 않습니다. 목록에 없는 파일이 생기고, 그런 파일은 찾을 길이 없습니다.
- **공개 저장 공간에 둠**: 주소를 만들 필요가 없고 빠릅니다. 주소를 아는 사람은 누구나 언제까지나 봅니다.
- **이미지를 데이터베이스에 넣음**: 접근 규칙이 한 곳에 모입니다. 데이터베이스가 빠르게 커지고 읽기가 무거워집니다.
- **모든 형식의 파일을 받음**: 문서나 코드도 붙일 수 있습니다. 내려받아 여는 파일은 위험을 따로 다뤄야 합니다. 사용자가 이미지만 받기로 했습니다.
