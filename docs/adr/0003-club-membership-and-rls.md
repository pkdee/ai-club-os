# 0003. Club 소속을 기준으로 데이터베이스에서 접근을 제한한다

## 상태

채택. 2026-10-10.

## 배경

요구 사항은 모든 Club 데이터를 소속과 역할로 격리하고, 그 규칙을 화면뿐 아니라 데이터베이스에서도 적용하라고 합니다. 앱은 브라우저에 공개되는 publishable key 로 Supabase 에 접속하므로, 데이터베이스가 직접 막지 않으면 다른 Club 의 데이터가 그대로 드러납니다. 첫 테이블인 `clubs` 와 `members` 를 만들면서 식별자 형식, 역할 표현, 접근 규칙의 틀을 함께 정했습니다.

## 결정

- 식별자는 uuid, 시각은 timestamptz 로 둡니다.
- 역할은 `members.role` 에 글자로 두고 `admin`(운영자)과 `member`(구성원)만 허용합니다. 역할이 잠정 결정이라 고치기 쉬운 check 제약을 썼습니다.
- 모든 테이블에 행 단위 보안을 켭니다. 조회는 그 Club 의 Member 에게만 허용합니다.
- Member 여부는 `private.is_club_member` 함수로 확인합니다. 이 함수는 Data API 에 노출되지 않는 `private` schema 에 두고 security definer 로 실행합니다.
- Club 은 로그인한 사용자 누구나 만들 수 있습니다. 만든 사람은 trigger 가 운영자 Member 로 넣습니다.
- 권한은 필요한 만큼만 줍니다. `authenticated` 는 `clubs` 조회, `clubs` 의 이름과 소개 입력, `members` 조회만 할 수 있습니다.
- 스키마 변경은 `supabase/migrations/` 의 SQL 파일로 남깁니다.

## 결과

- Club 을 만드는 요청은 만든 행을 되돌려 받을 수 없습니다. trigger 가 문장이 끝날 때 실행되어, 행을 되돌려 주는 시점에는 아직 Member 가 아니기 때문입니다. 앱은 결과를 받지 않고 목록을 다시 읽습니다.
- `members` 의 규칙이 `members` 를 직접 다시 읽으면 무한 반복이 됩니다. 그래서 Member 확인은 반드시 함수를 거칩니다.
- 다른 Member 의 이름과 이메일은 아직 볼 수 없습니다. `auth.users` 가 노출되지 않기 때문이며, Member 화면을 만들 때 프로필 구조가 필요합니다.
- 수정과 삭제는 규칙이 없어 모두 거부됩니다. 해당 기능을 만들 때 규칙을 추가합니다.
- 접근 규칙은 로컬 Postgres 17 에서 두 사용자와 로그인하지 않은 요청으로 13가지 경우를 손으로 시험했습니다. 자동 검증은 테스트 도구를 정할 때 함께 다룹니다.

## 검토할 대안

- **만든 사람에게 조회를 따로 허용**: 만든 행을 바로 되돌려 받을 수 있지만, 만든 사람이 Club 에서 빠진 뒤에도 계속 보이게 됩니다. 조회 기준을 소속 하나로 유지하려고 택하지 않았습니다.
- **Club 생성용 함수를 따로 노출**: 한 번의 호출로 Club 과 Member 를 만들 수 있지만 노출되는 API 가 늘고, 일반 권한으로는 규칙이 서로를 참조해 성립하지 않습니다.
- **역할을 enum 형식으로**: 값이 더 엄격해지지만 값을 바꾸거나 빼기가 번거롭습니다. 역할이 확정되면 다시 검토합니다.
