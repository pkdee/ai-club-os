# 0032. 로그인한 사용자 모두가 Club 목록을 보고, Club 마다 로고를 둔다

## 상태

채택. 2026-10-21 에 사용자가 요청했습니다. `0028-ai-log-images-in-storage.md` 에 이어 Storage 를 두 번째로 씁니다.

## 배경

처음 화면(`/`)은 내가 속한 Club 만 보여 주었습니다. Club 이 있는지 알려면 초대 링크를 받아야 했습니다.

사용자가 정했습니다. 로그인하면 등록된 Club 을 모두 본다. Member 가 아닌 Club 을 누르면 권한이 없다는 안내가 나온다. Club 에 아이콘이나 로고 같은 사진을 등록한다.

## 결정

### Club 목록

- `clubs` 와 `members` 의 접근 규칙은 그대로 둡니다. Club 안은 지금처럼 Member 만 봅니다. 내 Club 목록, Club 안쪽 화면, 계정 지우기가 이 규칙에 기댑니다.
- Member 가 아닌 사람은 `public.list_clubs()` 함수가 돌려주는 값만 봅니다. 이름, 소개, 로고 경로, Member 수, 만든 때, 내 역할입니다. 내 역할은 Member 가 아니면 비어 있습니다.
- Member 의 이름, 이메일, Club 안의 기록은 돌려주지 않습니다.
- 함수는 만든 사람의 권한으로 실행하고, 로그인한 사용자만 부릅니다. 로그인하지 않은 요청이 읽을 수 있는 것은 여전히 `get_presentation` 뿐입니다.
- 처음 화면은 "내 Club" 과 "다른 Club" 두 구역으로 나눕니다. 다른 Club 의 카드는 링크가 아닌 버튼이고, 누르면 "이 Club 에 들어갈 권한이 없습니다" 안내 창을 엽니다. 안내 창은 브라우저의 alert 대신 앱의 Dialog 를 씁니다.
- 참여 요청은 만들지 않았습니다. 안내 창은 운영자에게 초대 링크를 받으라고 알려 줍니다.

### 로고를 두는 곳

- 파일은 Supabase Storage 의 `club-logos` 에 둡니다. 공개하지 않는 저장 공간입니다.
- 경로는 Club 과 파일 이름의 두 마디입니다. 파일 이름은 앱이 만든 식별자와 확장자입니다. `clubs.logo_path` 가 지금 쓰는 파일을 가리킵니다.
- 형식은 PNG, JPEG, WebP, 크기는 한 장에 512KB 까지입니다. 앱, `clubs_logo_path_format` 제약, 저장 공간의 설정이 같은 값으로 막습니다. SVG 는 받지 않습니다.

### 올리는 순서

1. 브라우저가 고른 사진의 가운데를 정사각형으로 잘라 256px 로 줄입니다. WebP 로 만들고, 브라우저가 WebP 를 만들지 못하면 PNG 로 만듭니다. 원본은 PNG, JPEG, WebP, GIF 를 10MB 까지 고를 수 있습니다.
2. 서버 동작이 줄인 그림을 받아 새 이름으로 올립니다. 같은 자리에 덮어쓰지 않습니다.
3. `clubs.logo_path` 가 새 파일을 가리키게 합니다. 고치지 못하면 방금 올린 파일을 지웁니다.
4. 앞의 로고 파일을 지웁니다.

- AI Log 의 이미지와 달리 서버를 거칩니다. 줄인 그림은 서버 동작이 받는 요청의 크기 한도(1MB)보다 작습니다. 그래서 한 번짜리 표를 받는 단계와 목록 테이블이 필요 없습니다.

### 접근 규칙

- 그 Club 의 운영자만 올리고 지웁니다. 더 깊은 경로에는 올릴 수 없고, 고치는 규칙은 두지 않습니다.
- 로그인한 사용자는 모두 읽습니다. Club 목록이 모두에게 보이기 때문입니다.
- 화면은 앱의 `/clubs/<Club>/logo/<파일 이름>` 으로 로고를 받습니다. 이 주소는 로그인을 확인하고 Storage 에서 읽어 보냅니다. 파일 이름이 올릴 때마다 바뀌므로 브라우저가 1년 동안 기억하게 합니다.
- 보낼 때 형식을 짐작하지 못하게 하고(`nosniff`), 그 응답을 문서로 열어도 스크립트가 돌지 않게 합니다(`sandbox`).

### 파일과 Club 을 맞춰 두기

- 그 Club 의 자리에 로고 파일이 남아 있는 동안에는 Club 을 지우지 못합니다. 데이터베이스의 trigger 가 막습니다. Club 이 먼저 사라지면 그 파일을 지울 수 있는 운영자가 없어집니다.
- 그래서 Club 을 지울 때와, 계정을 지우면서 Club 이 함께 지워질 때 그 Club 의 자리에 있는 파일을 모두 먼저 지웁니다. AI Log 의 이미지를 지운 다음입니다.
- 앞의 로고를 지우지 못해 남은 파일도 이때 함께 지웁니다.

### 적용 전

- 마이그레이션 세 파일을 적용하기 전에는 Club 을 읽는 화면이 `logo_path` 열이 없다는 오류를 냅니다. 이번에는 적용 전에도 화면이 돌아가게 하는 분기를 두지 않았습니다.

## 결과

- 로그인한 사용자는 Member 가 아니어도 모든 Club 의 이름, 소개, 로고, Member 수를 봅니다. 개인 정보 안내에 적었습니다.
- Club 의 이름과 소개를 쓸 때 밖에서 보인다는 것을 생각해야 합니다. Club 설정의 로고 영역에 적었습니다.
- Club 을 숨기는 설정은 없습니다. 모든 Club 이 목록에 나옵니다.
- Club 을 지우는 일이 Storage 가 응답하는지에 기댑니다. 로고를 지우지 못하면 Club 을 그대로 두고 다시 시도하라고 안내합니다.
- 로고 주소가 앱을 거치므로 로고 하나마다 앱의 서버가 Storage 를 한 번 부릅니다. 브라우저가 기억하므로 같은 로고를 다시 받지 않습니다.
- Storage 는 올릴 때 적어 낸 형식만 확인합니다. 서버 동작이 형식과 크기를 다시 보지만 파일의 내용까지 들여다보지는 않습니다.
- 접근 규칙 시험 `tests/db/99e_club_directory_and_logos.test.sql` 이 목록 함수, 경로 제약, Storage 규칙, 지우는 순서를 봅니다. 실제 Supabase 프로젝트에서는 이 저장소에서 확인하지 못했습니다.

## 검토할 대안

- **`clubs` 의 읽기 규칙을 로그인한 사용자 모두로 넓힘**: 함수가 필요 없습니다. 하지만 `clubs` 를 읽는 모든 조회가 Member 가 아닌 Club 까지 받게 되어, 내 Club 목록과 계정 지우기가 따로 걸러야 합니다. 앞으로 `clubs` 에 열을 더할 때마다 밖으로 나가는지 따져야 합니다.
- **공개 저장 공간에 로고를 둠**: 앱을 거치지 않아 빠릅니다. 로그인하지 않은 사람도 주소만 알면 언제까지나 봅니다.
- **한 시간짜리 주소를 만들어 보여 줌**: AI Log 의 이미지처럼 화면을 열 때마다 주소를 만듭니다. Club 목록에 Club 이 많으면 주소를 만드는 요청도 많아지고, 주소가 바뀌어 브라우저가 기억하지 못합니다.
- **AI Log 의 이미지처럼 브라우저가 바로 올림**: 서버를 거치지 않습니다. 줄인 그림이 작아서 표를 받는 단계와 목록 테이블을 둘 만큼의 이점이 없습니다.
- **원본을 그대로 올림**: 브라우저에서 줄이는 코드가 필요 없습니다. 목록에서 작게 보이는 그림을 크게 받아야 하고, 정사각형이 아닌 사진은 잘려 보입니다.
